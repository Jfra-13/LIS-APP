Requerimientos Funcionales (RF) 

RF-01 [Gestión de Pacientes]: El sistema debe permitir al Técnico Administrativo registrar un nuevo paciente capturando sus datos demográficos básicos e identificador nacional (DNI), asignándole un UUID interno. 

RF-02 [Captura de Biometría]: El sistema debe permitir a la Enfermera de Triaje ingresar los signos vitales del paciente, específicamente: Presión Arterial, Frecuencia Cardíaca, Temperatura y Saturación de Oxígeno. 

RF-03 [Cálculo Algorítmico]: El sistema debe evaluar automáticamente los datos del RF-02 y asignar un nivel de urgencia (I al V) en el mismo instante de guardar el registro, bloqueando el campo para evitar manipulación humana. 

RF-04 [Cola Dinámica]: El sistema debe listar a los pacientes en el panel del Médico Especialista, reordenándose en tiempo real de acuerdo a la RN-02 cada vez que ingresa un nuevo triaje. 

RF-05 [Historia Clínica Narrativa]: El sistema debe proporcionar al Médico Especialista un área de texto libre enriquecido para ingresar el motivo de consulta, la evolución y el diagnóstico clínico presuntivo. 

RF-06 [Disparador de Eventos NLP]: Al momento de que el Médico guarde el registro (RF-05), el sistema debe emitir una señal (Signal) que capture el texto y lo envíe a una cola de mensajería, actualizando el estado visual del registro a "Procesando IA". 

RF-07 [Sugerencia de Código CIE-10]: El sistema debe permitir a un agente autónomo actualizar la base de datos con un código internacional CIE-10 sugerido tras procesar exitosamente el texto del médico. 

Requerimientos No Funcionales (RNF) 

RNF-01 [Arquitectura Asíncrona - Rendimiento]: Para evitar la latencia en la pantalla del médico, el motor de Inteligencia Artificial (NLP) debe ejecutarse de manera desacoplada utilizando un Message Broker (RabbitMQ) y procesos en segundo plano (Celery Workers). 

RNF-02 [Tiempos de Respuesta - UX]: Las operaciones CRUD (Crear, Leer, Actualizar, Eliminar) en los formularios de admisión y triaje deben procesarse y renderizarse en un tiempo no mayor a 1.5 segundos. 


RNF-03 [Contenerización - Portabilidad]: Todos los microservicios del ecosistema (Web Server, Database, Message Broker, Worker NLP) deben estar aislados y orquestados mediante contenedores (Docker y Docker Compose) para garantizar el despliegue en cualquier servidor hospitalario sin conflictos de entorno. 

RNF-04 [Integridad y Seguridad de Datos]: Las llaves primarias (Primary Keys) de las tablas transaccionales críticas (Pacientes y Triajes) no deben ser autoincrementales, sino generar identificadores universales (UUIDv4) para prevenir la predicción de URLs y auditorías maliciosas. 

RNF-05 [Pila Tecnológica]: El sistema debe ser desarrollado utilizando Python (Django) para el backend, PostgreSQL como motor de base de datos relacional, y la librería spaCy para el procesamiento del modelo de lenguaje natural en español.



Resultados Esperados 
Clasificación clínica determinística y sin errores humanos: Estandarización total de los niveles de urgencia en la admisión. El sistema aplica reglas de negocio estrictas sobre los signos vitales, garantizando un cálculo de prioridad objetivo y manteniendo la inmutabilidad legal del registro primario.

Alta disponibilidad y optimización del flujo médico: Reducción drástica del tiempo de interacción del personal de salud con el software. Gracias a la implementación de una Arquitectura Orientada a Eventos (EDA) con procesamiento asíncrono en segundo plano, la asignación y transición de pacientes en la cola de atención ocurre en milisegundos, sin bloquear la interfaz gráfica.

Soporte Diagnóstico Estructurado (CIE-10): El 100% de las atenciones contarán con sugerencias automáticas de códigos CIE-10 al finalizar la nota médica. Este proceso es impulsado por un motor de sugerencias determinístico basado en catálogos JSON versionados, lo que asegura resultados rápidos, predecibles y auditables (sin la latencia o "cajas negras" asociadas a modelos de Machine Learning), acelerando así el ciclo de ingresos financieros del hospital.

Trazabilidad absoluta e inmutabilidad: Generación de un registro histórico exhaustivo sobre los tiempos exactos y los cambios de estado en la atención del paciente (desde En Espera hasta En Consultorio). Este control transaccional estricto sirve como una fuente confiable de indicadores clave de rendimiento (KPIs) para la gestión y auditoría hospitalaria.

Stack:
1. Frontend (Capa de Presentación e Interacción)
La interfaz de usuario está diseñada para ser rápida, responsiva y dinámica sin depender de frameworks complejos de JavaScript (como React o Angular), priorizando la velocidad de carga en entornos hospitalarios.

HTML5 / CSS3: Lenguajes base para el maquetado y estilos.

Bootstrap: Framework de diseño utilizado para garantizar que la interfaz sea responsiva (adaptable a pantallas de escritorio en consultorios o tablets en áreas de triaje) y para proveer componentes UI estandarizados (modales, alertas, tarjetas).

HTMX (django-htmx): Herramienta clave para el dinamismo. Permite realizar peticiones asíncronas (AJAX) directamente desde los atributos HTML para actualizar partes específicas de la pantalla (como la Cola de Estados) sin tener que recargar la página completa, brindando una experiencia de "Single Page Application" (SPA) nativa.

Django Templates: Motor de plantillas renderizadas del lado del servidor (SSR) que inyecta los datos clínicos de forma segura antes de enviarlos al navegador del cliente.

2. Backend (Lógica de Negocio y Core Médico)
El motor principal del sistema, diseñado bajo el patrón arquitectónico MVT (Model-View-Template) y principios SOLID.

Python 3.12: Lenguaje de programación principal. Su versión reciente garantiza un rendimiento óptimo y tipado estricto.

Django 5.0: Framework web de alto nivel. Se eligió por su robustez en la seguridad (protección CSRF, XSS, inyección SQL por defecto), su sistema de autenticación integrado y su potente panel de administración (adaptado para el back-office médico).

Django ORM: Mapeador Objeto-Relacional utilizado para interactuar con la base de datos mediante código Python, garantizando abstracción y seguridad en las consultas.

3. Arquitectura Orientada a Eventos (Asincronismo y Conexiones)
Para evitar cuellos de botella cuando hay un alto volumen de pacientes, los procesos pesados se han desacoplado del flujo principal HTTP.

RabbitMQ: Actúa como el Message Broker (Enrutador de mensajes). Recibe los eventos del sistema (por ejemplo, "Nuevo triaje guardado") y los encola de forma segura en memoria hasta que haya un trabajador disponible para procesarlos.

Celery (v5.6): Gestor de colas de tareas asíncronas (Worker). Consume los mensajes de RabbitMQ en segundo plano para realizar transiciones de estado complejas (como mover pacientes a EN_CONSULTORIO) sin congelar la pantalla del enfermero o médico.

4. Persistencia de Datos (Base de Datos)
PostgreSQL 15: Sistema de Gestión de Bases de Datos Relacionales (RDBMS) de nivel empresarial.

Justificación: Elegido por su cumplimiento ACID estricto, soporte nativo para campos UUID (identificadores únicos seguros para registros médicos) y manejo avanzado de restricciones (constraints) a nivel de base de datos para garantizar la integridad de la historia clínica.

5. Procesamiento y Diagnóstico (Reglas Clínicas)
SpaCy: Librería de Procesamiento de Lenguaje Natural (NLP) industrial. Utilizada en el sistema para normalizar textos médicos y extraer palabras clave (keywords) de forma rápida, permitiendo que el motor determinístico cruce estas palabras con el catálogo JSON y sugiera códigos CIE-10 de manera precisa y sin la latencia de un modelo pesado de Machine Learning.

6. Aseguramiento de la Calidad (QA) y Testing
Garantizan que las reglas de negocio médicas no fallen al integrar nuevo código.

Pytest & Pytest-Django: Framework principal para ejecutar las pruebas unitarias, de integración y End-to-End (E2E).

Factory_boy: Generador de datos sintéticos. Crea cientos de pacientes y triajes ficticios en milisegundos para someter al sistema a pruebas de estrés y comportamiento.

Coverage: Herramienta de auditoría que mide el porcentaje de código fuente que está siendo validado por las pruebas automatizadas (buscando un umbral mínimo del 80%).

Flake8 y Black: Linters y formateadores estáticos que imponen estándares de escritura de código PEP-8 de forma implacable.

7. Infraestructura, Contenedores y CI/CD (DevOps)
Docker & Docker Compose: Todo el entorno (Web, DB, RabbitMQ, Worker) está "containerizado". Esto garantiza que el sistema funcione de manera idéntica en la computadora de desarrollo, en los servidores de prueba y en producción.

Jenkins / GitHub Actions: Servidor de Integración Continua (CI). Intercepta cada nuevo Pull Request o actualización de código, levanta la infraestructura en la nube, ejecuta todas las pruebas (QA) y solo permite integrar el código a la rama principal (main/master) si no hay ningún error, garantizando cero regresiones.
